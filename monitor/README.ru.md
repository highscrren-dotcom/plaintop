# monitor — текстовый монитор

[English](README.md) · Русский

Текстовый монитор системы для рабочего стола Plasma 6, на QML. Работает в двух хостах —
плазмоидом и окном со сквозными кликами, — и оба рисуют одно и то же одним кодом. Почему
вообще плазмоид — `../docs/DECISIONS.ru.md`, решение 1; откуда данные — решение 2.

| Путь | Что это |
|---|---|
| `shared/MonitorData.qml` | подписки, разовые чтения, редкие команды и сборка строк по описанию |
| `shared/MonitorView.qml` | рисует эти строки; палитра живёт здесь, а каждый кусок строки несёт роль, а не цвет |
| `shared/SensorRegistry.qml` | какие датчики есть у этой машины; находит привязанные к машине идентификаторы и ранжирует сетевые интерфейсы |
| `package/` | хост-плазмоид, со штатным диалогом настроек Plasma |
| `window/window.qml` | хост со сквозными кликами: окно с `Qt.WindowTransparentForInput` |
| `window/settings.qml` | редактор оконного хоста, с живым просмотром настоящим движком |
| `window/setup.py` | раскладывает окно, пишет правило KWin и автозапуск, переносит настройки из плазмоида |
| `generate.py` | `../schema/*.json` → `package/contents/code/description.js`; проверяет прежде чем писать |

`install.sh` копирует общие файлы в тот хост, который ставит. Две правленные копии одного
QML — верный способ тихо разъехаться; `./install.sh --status` сверяет каждый хост с самим
`shared/`.

## Что показывает

Заголовок с именем хоста, часы, дату, систему, загрузку CPU общую и по узлам NUMA, модель
процессора с температурами и оборотами, топ процессов по CPU и памяти, ОЗУ, GPU с VRAM,
диски с температурой NVMe, аптайм, сеть, состояние docker/ollama/обновлений и паспорт
железа — всё, что показывала conky-реализация.

**Набор и порядок блоков — из описания** (`../schema/widget.json`): включить, выключить,
переставить, поменять параметры, добавить свой блок — произвольной командой или любым
датчиком ksystemstats. Правят его оба хоста: плазмоид — на странице «Блоки» своего
диалога, окно — в своём редакторе.

## Зачем два хоста

Плазмоид на рабочем столе не отдаёт левую кнопку мыши — четыре способа проверены, см.
`../docs/GOTCHAS.ru.md`; настройка «Мышь» освобождает только правую. Обычное окно с
`Qt.WindowTransparentForInput` отдаёт обе, поэтому монитор может лежать поверх стола, не
отбирая клики у ярлыков под ним.

Чем за это платит оконный хост: нет штатного диалога настроек, нет управления сессией и
нет самостоятельного размещения — под Wayland окно не может задать себе место, поэтому
место, размер, «держать снизу» и «мимо панели задач» задаются правилом KWin по заголовку.

## Установка

```bash
./install.sh --plaintop-window     # разложить, записать правило KWin и автозапуск, запустить
./install.sh --plaintop-export     # перенести текущие настройки плазмоида в файл окна
./install.sh --plasmoid            # хост-плазмоид (на стол не сажается, если есть окно)
./install.sh --status              # оба хоста
```

На столе должен быть один хост: они рисуют одно и то же.

⚠️ `--plasmoid` перезапускает оболочку, и не для красоты: plasmashell держит QML пакета в
кэше, и без перезапуска виджет остаётся со старой разметкой — `../docs/GOTCHAS.ru.md`.
Плазмоид добавляется на рабочий стол как обычный виджет, либо скриптом:

```bash
qdbus6 org.kde.plasmashell /PlasmaShell org.kde.PlasmaShell.evaluateScript \
  'desktops()[0].addWidget("org.s1dd1.plaintop", 60, 800, 420, 220)'
```

## Настройки

**Плазмоид** держит настройки в хранилище Plasma: схема — `package/contents/config/main.xml`,
в диалоге две страницы — «Общее» (шрифт, размеры, отступы, четыре цвета палитры, мышь,
интервалы) и «Блоки», где живёт и текст заголовка — по умолчанию пустой, так что
свежая установка показывает только имя хоста.

**Окно** читает `~/.config/plaintop/monitor.json` — внешний вид и описание блоков в одном
файле: шрифт, кегль, отступы, размер виджета, интервал обновления, четыре цвета палитры и
`blocks`. Файл перечитывается каждые две секунды, поэтому правка видна без перезапуска.
`processInterval` — раз во сколько секунд читать список процессов для топов: это самое
дорогое в сборе — около 3 % ядра при 2 с по умолчанию и около 1,3 % при 10 с (измерено
при ~900 процессах).

**Редактор окна — `window/settings.qml`**, запускается пунктом меню «plaintop — монитор»
или `./install.sh --plaintop-settings`. Он показывает раскладку **настоящим движком**
рядом с настройками — тот же `MonitorView`, которым рисует рабочий стол, с собственным
`MonitorData`, так что правка видна раньше, чем сохранена. Писать файлы QML не умеет,
поэтому редактор читает у реле `GET /config?widget=monitor` и отправляет правки обратно;
единственным писателем остаётся реле. `--plaintop-export` по-прежнему забирает то, что
сохранил диалог плазмоида.

**Вписывать руками ничего не нужно.** Параметр, который держит привязанный к машине
идентификатор, предлагается списком того, что эта машина отдаёт: датчики из дерева с живым
значением подсвеченного, сетевые интерфейсы, точки монтирования из `/proc/self/mounts`.
Какие это параметры, редактор узнаёт из `pick` в словаре — новый тип блока правки
редактора не требует. Пустое значение означает «найти самому», а сохранённое — лишь
предпочтение; см. решение 6 в `../docs/DECISIONS.ru.md`. Под меню интерфейсов редактор
пишет, на каком интерфейсе остановился автопоиск, — и пишет это же, когда сохранённого
интерфейса на машине больше нет.

Чтобы сдвинуть окно, поправьте правило KWin (Параметры системы → Правила окон) или
запустите `--plaintop-window` с переменными `PLAINTOP_X` / `PLAINTOP_Y`. Зазор от края
экрана рисуется внутри виджета (`padLeft`, `padTop`) — поэтому правило держит окно в `0,0`.

## Источники данных

Данные берутся у **ksystemstats** через `org.kde.ksysguard.sensors` — сотни готовых
датчиков, — а списки процессов у `org.kde.ksysguard.process`. Команды добирают только то,
чего у датчиков нет: раскладка узлов NUMA, модель процессора и плата читаются один раз при
старте (`/sys`, `lscpu`), заполненность по точкам монтирования — `df` раз в 10 с,
docker/ollama/обновления — `package/contents/code/services.sh`, плюс ваши блоки-команды.
Отвергнутые способы и цена каждого — `../docs/DECISIONS.ru.md`, решение 2.

## Что предстоит

- **Температуры по пакетам CPU** — сейчас берётся максимум по ядрам узла; в сенсорах
  `coretemp-isa-000N` нет, за пакетами придётся идти в `sensors -u` редким запуском.
- **Чтение и запись диска** в строке «/» — у conky там было `R:` и `W:`.
- **Генератор для conky** — слой описания задумывался общим на оба движка; сейчас
  генератор только один.
