# schema — описание виджета

[English](README.md) · Русский

Два файла, оба **от движка не зависят**:

- **`widget.json`** — раскладка: какие блоки, в каком порядке, с какими параметрами.
- **`blocks.json`** — словарь типов блоков: какие есть, какие параметры принимают.
  Диалог настроек строится по нему, а не по списку в коде — иначе новый тип блока
  требовал бы правки интерфейса.

Запись блока:

```json
{ "id": "cpu", "type": "cpu", "enabled": true,
  "params": { "per_socket": true, "model_line": true, "top_processes": 5 } }
```

## Как это попадает в виджет

```
schema/widget.json ─┐
                    ├─ monitor/generate.py ──→ package/contents/code/description.js ─→ main.qml
schema/blocks.json ─┘
```

Генератор проверяет описание (неизвестный тип блока, незаявленный параметр, неверный
тип значения) и проставляет значения по умолчанию из словаря. Негодное описание
останавливает установку — лучше отказ, чем пустой виджет и поиск причины в QML.

⚠️ Почему JS, а не чтение JSON из QML: в plasmashell запрещён `XMLHttpRequest`
к `file://` (`../docs/GOTCHAS.ru.md`), а импорт `.js` работает.

`description.js` генерируется и в git не хранится — правится только `schema/*.json`.

## Открытые типы блоков

Два типа не привязаны к конкретной величине и делают словарь расширяемым без правки кода:

- **`command`** — строка из вывода произвольной команды со своим интервалом;
- **`sensor`** — любой датчик ksystemstats по его id, с полоской или без.

## Параметры, которые машина заполняет сама

Параметр в словаре может сказать, что именно он хранит, — и тогда редактор предложит собственный
список машины, вместо того чтобы спрашивать идентификатор:

```json
"nvmeSensor": { "type": "string", "name": "Датчик температуры NVMe (пусто — найти самому)",
                "default": "", "pick": "sensor",
                "pattern": "^lmsensors/nvme-[^/]+/temp\\d+$" }
```

- **`pick`** — `sensor` (всё, что отдаёт ksystemstats, из того же реестра, который читает
  виджет), `iface` (сетевые интерфейсы, найденные в дереве датчиков) или `mount` (точки
  монтирования из `df`). Страница «Блоки» предлагает список рядом с полем: выбор заменяет
  строку либо добавляется к списку; поле остаётся местом, где можно вписать своё.
- **`pattern`** — сужает список и служит тем, на что опирается сам виджет.

Типы параметров: `bool`, `int` (можно `min`/`max`), `string`, `stringlist` и `enum` — строка
из собственных `values` параметра, в диалоге показанная соответствующим `names`:

```json
"format": { "type": "enum", "name": "Hours", "default": "24h",
            "values": ["24h", "12h", "locale"],
            "names": ["24-hour", "12-hour", "as the locale says"] }
```

Кроме параметров у блока могут быть два собственных поля: `name` — ваша подпись, видная в
списке, и `column` — 2 для второй колонки виджета.

Сохранённое значение — **предпочтение**, а не требование: оно побеждает, пока машина его отдаёт, а
когда перестаёт — замену находит `pattern`. Пустое значение сразу означает «найти самому» — поэтому
в раскладке из `widget.json` нет идентификаторов датчиков той машины, на которой её писали.
См. решение 6 в `../docs/DECISIONS.md`.

## Правка из интерфейса

Страница «Блоки» в настройках виджета читает ту же раскладку: включить, выключить,
переставить, добавить блок любого типа из словаря, дублировать, убрать, подписать,
отправить во вторую колонку, поправить параметры — и кладёт результат строкой JSON в
настройки плазмоида. Пока там пусто, берётся раскладка из пакета; кнопка «Сбросить»
возвращает её. Тот же JSON показан внизу страницы — прочитать, поправить или вставить с
другой машины; «Применить JSON» сначала сверяет его со словарём.
