# Грабли: виджет на рабочем столе под KDE Plasma 6 / KWin Wayland

[English](GOTCHAS.md) · Русский

Собрано при настройке на s1dPC 20.09.2026. Всё подтверждено исполнением на живой
системе — здесь нет ничего «по документации» или «по памяти».

Две части: сначала conky (первая реализация), затем плазмоид (целевая).

# Часть I. conky

## Conky под Wayland работает

Расхожее «Conky под Wayland не работает» — неверно для KDE. Он идёт через XWayland
(`Xwayland :0 -rootless` поднимается KWin автоматически) и ведёт себя штатно.

⚠️ Настоящие ограничения лежат не там, где их обычно ищут — см. ниже.

## Тип окна: только `normal`

| Тип | Окно создаётся | Прозрачность |
|---|---|---|
| `normal` | да | **да** |
| `desktop` | да, свойство ставится верно | **нет — чёрный прямоугольник** |
| `override` | да | нет (сказано в man: «semi-transparent backgrounds do not work») |

С `desktop` KWin перестаёт композитить окно. Проверено: вокруг текста появляется
непрозрачная чёрная подложка.

Рабочая связка:
```lua
own_window_type = 'normal',
own_window_hints = 'undecorated,below,sticky,skip_taskbar,skip_pager',
own_window_colour = '#00000000',
```

⚠️ `own_window_transparent` и `own_window_argb_value` объявлены устаревшими в conky 1.24,
`own_window_argb_visual` удалён. Прозрачность задаётся только через `own_window_colour`.
Старые гайды в интернете почти все написаны под удалённые ключи.

## Click-through: своей настройки у conky НЕТ

В конфиге всего шесть ключей `own_window_*`, и ни один не делает окно прозрачным для
мыши. Xshape в сборку вкомпилирован («Xshape extension (click through)» в `conky --version`),
но наружу не выведен.

Решение — поставить окну **пустую область ввода** извне, через расширение X Shape
(`conky/clickthrough.py`, нужен `python-xlib`).

Проверка результата — чтением обратно, а не на глаз:
```
Bounding (что рисуется): 440x748
Input    (что ловит мышь): 0 прямоугольников   ← клики проходят
```

⚠️ **Проверять через `xdotool mousemove` бесполезно.** Под Wayland синтетические движения
мыши блокируются: курсор не двигается, `getmouselocation` возвращает окно под его реальным
положением, и тест молча показывает не то. На этом легко сделать ложный вывод «работает».

## Кто запускает conky — путей много, все не перекрыть

Симптом: после перезагрузки на экране чужой conky либо свой, но ловящий клики.

Найденные источники, все реальные:
1. **`ksmserver`** — менеджер сеансов KDE сохраняет conky (он регистрируется по XSMP)
   и поднимает при входе. Лечится `excludeApps` в `ksmserverrc`.
2. **KWin + пакетный desktop-файл** — KWin ведёт СВОЮ сессию
   (`~/.config/session/kwin_saved at previous logout_`), сопоставляет `resourceClass=Conky`
   с `/usr/share/applications/conky.desktop` из пакета и запускает **его**
   (`Exec=conky --daemonize --pause=1`) с дефолтным конфигом.
3. **KWin по сохранённой команде** — поднимает нашу команду напрямую, мимо скрипта запуска.

**Вывод, ради которого написан этот раздел: не перебирать запускающих.** Их больше, чем
кажется, и каждый всплывает только после очередной перезагрузки. Правильно — сделать
операцию идемпотентной: запуск условный, нужное состояние применяется **всегда**.

Чем закрыто (слои независимы намеренно):
- `own_window_class = 'conky-plainext'` — разрывает сопоставление с пакетным desktop-файлом;
- `~/.local/share/applications/conky.desktop` с `Hidden=true` — перекрывает системный файл,
  каталог пользователя идёт раньше в `XDG_DATA_DIRS`;
- `start.sh` гасит чужие экземпляры и применяет click-through независимо от того, кто
  поднял conky.

⚠️ `excludeApps` держать в согласии с `own_window_class`: после смены класса старое
значение перестаёт совпадать и исключение молча выключается.

## Мелочи, стоившие времени

- **`pkill -f 'conky -c'` убивает собственную оболочку** — шаблон совпадает с её командной
  строкой. Только `pkill -x conky`.
- **`bat cache --build` не подхватывает тему с первого раза** — нужен второй прогон.
  Проверка: `bat --list-themes | grep tokyo`.
- **Датчики брать по ИМЕНИ чипа** (`coretemp-isa-0000`, `nct6779-isa-0a20`), а не по
  индексу `hwmon` — индексы плавают между перезагрузками.
- **`${if_mounted}` не спасает от `statfs`-ошибки**: conky регистрирует файловые объекты
  до проверки условия, и на несмонтированном пути один раз пишет ошибку в лог. Безвредно.
- **Lua 5.4 запрещает присваивать переменной цикла** — `for v in ... do v = tonumber(v)`
  падает на `attempt to assign to const variable`.
- **Чистить конфиги фильтром по слову опасно.** Удаление всех строк со словом `conky` из
  `ksmserverrc` снесло заодно `excludeApps=conky` — то есть отключило защиту, поставленную
  строкой выше. Порядок: сначала чистка, потом запись.

## Ловушки самих скриптов

- **`set -o pipefail` + `grep -q` врут вместе.** `fc-list | grep -q 'шрифт'` возвращает
  ошибку, даже когда шрифт есть: `grep -q` выходит на первом совпадении, `fc-list` ловит
  `SIGPIPE`, и при `pipefail` весь конвейер считается упавшим. Проверка молча показывает
  «не найдено». Лечится отказом от конвейера — здесь через `fc-match -f '%{family}'`.

# Часть II. плазмоид

## Чтение файлов из QML в plasmashell запрещено

`XMLHttpRequest` к `file:///proc/stat` не работает: Qt отвечает «Using GET on a local file
is disabled by default. Set `QML_XHR_ALLOW_FILE_READ` to 1». Переменная задаётся процессу
**всей оболочки**, то есть ослабляет доступ к файлам для любого QML внутри неё, и требует
перелогина. Проверено: в журнале plasmashell предупреждение на каждый тик, данных ноль.

⚠️ Отсюда и решение 2 в `DECISIONS.md`: данные берутся у ksystemstats по подписке,
а не вычитываются из `/proc` своими руками.

## plasmashell держит QML пакета в кэше

Переустановки пакета мало. Пересоздания апплета на рабочем столе — тоже мало.
Проверено метками в `Component.onCompleted`: новый код не выполнялся ни после
`kpackagetool6 --upgrade`, ни после `remove()` + `addWidget()`; метка появилась
только после `systemctl --user restart plasma-plasmashell.service`.

Поэтому `./install.sh --plasmoid` перезапускает оболочку сам — иначе правка молча
не доедет, а время уйдёт на поиск несуществующей ошибки в QML.

📝 Метки для таких проверок ставить через `console.warn`: он в журнале виден точно.

## Скриптинг plasmashell — не полноценный QML

В `org.kde.PlasmaShell.evaluateScript` **нет объекта `Qt`**: `Qt.rect(...)` падает
с `ReferenceError: Qt is not defined`. Присваивание `widget.geometry` обычным
JS-объектом `{x, y, width, height}` проходит молча и **ничего не меняет**.

Место и размер задаются только аргументами при создании:

```js
desktops()[0].addWidget("org.s1dd1.plaintop", 48, 44, 440, 815)
```

Размер при этом подгоняется под сетку: 440x815 превращается в 448x816.

## Движка `systemmonitor` в Plasma 6 нет

Каталог движков — `/usr/lib/qt6/plugins/plasma5support/dataengine/`, и `systemmonitor`
в нём отсутствует: есть `executable`, `time`, `powermanagement`, `soliddevice` и погодные.
Весь мониторинг переехал в ksystemstats (`org.kde.ksysguard.sensors`).

## Сенсоры отвечают не мгновенно

Демон `ksystemstats` поднимается по первой подписке, и 1–1,5 с сенсор находится
в состоянии «грузится» (`status: 1`). На старте надо рисовать прочерк: ноль в этот
момент — неправда, а не значение.

📝 Замер сделан в отдельном QML-движке той же версии Qt, не внутри оболочки.

## Готовое форматирование ломает моноширинные колонки

`formattedValue` и `Formatter` вставляют невидимые U+200B перед «%», U+2009 перед «°C»
и U+00A0 в разделителе тысяч. В тексте, где колонки держатся на равной ширине символа,
это видно сразу. Берём сырой `value` и форматируем сами.

📝 Проверено там же — в отдельном движке; внутри оболочки формат не перепроверялся,
потому что готовое форматирование мы и не используем.

## Размер апплета задаётся `Layout.*` на корне — и только постоянный

`implicitWidth/Height` внутри `fullRepresentation` контейнер не спрашивает: размер он
берёт из `Layout.minimum*`/`Layout.preferred*` **на корневом `PlasmoidItem`**.

⚠️ И подсказка должна быть постоянной. Пока она считалась от высоты текста, контейнер
пересобирал раскладку при каждом изменении числа строк — а строки прибывают по мере
прихода данных (диски через 10 с, службы через 15 с). Каждая пересборка сбрасывала
виджет в угол 0,0. Проверено многократно.

## Место апплета программно не закрепляется

Перепробовано, всё проверено исполнением:

| Попытка | Итог |
|---|---|
| `addWidget(type, x, y, w, h)` | координаты игнорируются |
| `widget.geometry = {x, y, …}` в скриптинге | проходит молча, ничего не меняет |
| `Qt.rect(...)` там же | `ReferenceError: Qt is not defined` |
| Запись `ItemGeometries` в конфиг при живой оболочке | затирается самой оболочкой |
| То же при остановленной оболочке | **plasmashell всё равно ставит апплет в 0,0** |

Поэтому зазор от края рисуется **внутри** виджета (настройки «Отступ слева/сверху»),
а не координатами апплета: так он держится независимо от того, куда контейнер поставил
апплет, и переживает перезапуск оболочки.

## systemd глушит plasmashell после частых перезапусков

При отладке QML оболочка перезапускается на каждую правку, и через несколько подряд
systemd отвечает «start request repeated too quickly» — рабочий стол остаётся без
панели. Лечится `systemctl --user reset-failed plasma-plasmashell.service` и повторным
`start`. Между перезапусками нужна пауза; `install.sh --plasmoid` делает один.

## Логи Qt уходят в journald, а не в stderr

`console.warn` из QML не виден в терминале — сообщение уходит в журнал. Это не особенность
plasmashell: на этой системе (на базе Arch) любая программа на Qt пишет в journald,
как только stderr — не терминал, так что конвейер или перенаправление в файл не получают
ничего, а `journalctl --user` сообщения показывает. `QT_FORCE_STDERR_LOGGING=1`
возвращает их — и для `qml6`, и для `qmltestrunner` в скрипте; иначе кажется, что код
вообще не выполняется.

## Роли моделей ksysguard берутся по имени

Номера ролей у моделей разные: `Value` — 265 у `SensorDataModel` и 256 у
`ProcessDataModel`. Зашивать числа нельзя, но и угадывать не нужно: enum доступен
в QML как `Sensors.SensorDataModel.Value` и `Proc.ProcessDataModel.Value`.

⚠️ У `KSortFilterProxyModel` сортировка задаётся `sortRoleName: "Value"`;
с `sortRole` компонент не строится вовсе.

## `http://127.0.0.1` разрешён, `file://` — нет

Запрет XHR касается только локальных файлов. Запрос к локальному HTTP-серверу изнутри
`plasmashell` проходит: проверено пробой в установленной копии виджета, она записала в
журнал `status=200` и полное тело ответа. То есть блоку, которому нужны данные, каких нет
ни в одном сенсоре, не обязателен компилируемый плагин — хватит небольшой локальной службы.

⚠️ Цена сидит в опросе, а не в рисовании. Измерено на s1dPC: кольцо из 120 штрихов
элементами сцены стоит 3,9 % одного ядра при 30 обновлениях в секунду, а один только
опрос тех же данных по HTTP 45 раз в секунду с разбором JSON — 6,3 %. Частота и размер
полезной нагрузки важнее формы.

## Анимация преобразования дороже данных, которые она анимирует

То же кольцо, те же данные: 3,9 % одного ядра стоя при 30 кадрах, 12,3 % вращаясь при 60,
26,4 % если рисовать на `Canvas` вместо элементов сцены. Если движения нет в данных, оно
не стоит своей цены.

## Левую кнопку держит обёртка апплета — и её можно отключить

`enabled: false` у полного представления отдаёт только **правую** кнопку: контекстное
меню стола (и меню ярлыка) открывается сквозь виджет, а левый клик до стола не доходит.
Держит его не апплет. plasmashell заворачивает каждый апплет на столе в
`AppletContainer` — QML-`BasicAppletContainer` поверх C++-`ItemContainer`
(`plasma-workspace/components/containmentlayoutmanager/itemcontainer.cpp`); апплет — его
`contentItem` и прямой потомок. Всё решают три вызова в конструкторе:

```cpp
setFiltersChildMouseEvents(true);         // видит нажатие раньше апплета
setAcceptedMouseButtons(Qt::LeftButton);  // хочет только левую — потому правая и проходит
setKeepMouseGrab(true);                   // и не даёт её отобрать
```

`ItemContainer::mousePressEvent` заканчивается `event->accept()` при любом
`editModeCondition`, кроме `Manual`, который выходит раньше, — но и он оставляет нажатие
себе, потому что Qt принимает событие мыши *до* доставки (`qquickdeliveryagent.cpp`,
`deliverMatchingPointsToItem`: `pointerEvent->accept();` прямо перед
`QCoreApplication::sendEvent`). Уровнем ниже `AppletsLayout::mousePressEvent` делает
`event->setAccepted(false)`, если ни один контейнер не в режиме правки, так что нажатие,
которое контейнер не взял, идёт дальше — к папке на столе и к containment. Вся проблема —
в обёртке.

Четыре попытки, все исполнены, все мимо по левой кнопке — и строка, о которую разбилась
каждая:

| Попытка | Итог | Строка |
|---|---|---|
| `enabled: false` у полного представления | правая кнопка проходит, левая нет | `setAcceptedMouseButtons(Qt::LeftButton)`: правую контейнер и не хотел, а левую фильтрует раньше, чем её увидит потомок |
| `locked = true` через скриптинг plasmashell | в Plasma 6 свойство только читается, остаётся `false` | до контейнера ничего не дошло |
| `immutability=2` у containment | применилось и пережило перезапуск, левая по-прежнему перехвачена | containment стола ставит `editModeCondition: Plasmoid.immutable ? Locked : AfterPressAndHold`, а `Locked` всё равно доходит до `event->accept()` |
| `immutability=2` у containment **и** у каждого апплета | условие должно стать `Manual`, а левая всё равно перехвачена | `ItemContainer::editModeCondition()` отвечает `Locked`, пока заблокирована раскладка; а `Manual` Qt и так принял бы заранее |

Выход — в списке целей Qt, а не во флагах Plasma. `eventTargets` пропускает потомка, у
которого `!isVisible() || !isEnabled() || culled`, — отключённый элемент со всем своим
поддеревом никогда не становится целью мыши, ни для одной кнопки. Из QML апплета
контейнер — это `root.parent`, а `enabled` — публичное записываемое свойство любого
`QQuickItem`:

```qml
readonly property bool shellEditMode: (Plasmoid.containment && Plasmoid.containment.corona)
    ? Plasmoid.containment.corona.editMode : false

Binding {
    target: root.parent
    property: "enabled"
    value: !root.cfg.clickThrough || root.shellEditMode
    when: root.parent !== null && ("editModeCondition" in root.parent)
}
```

`Plasmoid.containment → .corona → .editMode` — публичные `Q_PROPERTY` libplasma
(`applet.h`, `containment.h`, `corona.h`), так что виджет видит режим правки оболочки и
возвращает обёртку ровно на это время — в режиме правки обёртка снова включена (проверено
через DBus), так что работают штатные ручки оболочки: двигать, растягивать, настраивать.
Условие `when` привязывает только когда у родителя есть `editModeCondition`, то есть это
`ItemContainer`, — и потому не трогает `plasmawindowed` и превью. Представление сохраняет
свой `enabled: !root.cfg.clickThrough`, чтобы в режиме правки мышь брала обёртка, а не
виджет.

⚠️ Пока клики проходят насквозь, по виджету нельзя щёлкнуть и правой кнопкой. К
настройкам ведут режим правки рабочего стола или `./install.sh --clicks-off`.

⚠️ Отключать обёртку — путь только для виджета, в котором нечего нажимать: монитора и
погоды. Где кнопки должны работать — плеер и визуализатор с плеером в кольце, — обёртка
остаётся включённой и получает `containmentMask` поверх кнопок: «Частичная
`containmentMask` на обёртке» ниже (решение 11).

Проверено в два шага:

- **Стенд**, `tests/passthrough.qml`: файл QtTest, импортирующий установленный
  `org.kde.plasma.private.containmentlayoutmanager` — те же скомпилированные классы, что
  у plasmashell, — с `AppletsLayout`, двумя `ItemContainer` над считающими `MouseArea` и
  ещё одной `MouseArea` снизу вместо стола. `./install.sh --check-passthrough` запускает
  его без экрана (`QT_FORCE_STDERR_LOGGING=1 QT_QPA_PLATFORM=offscreen
  /usr/lib/qt6/bin/qmltestrunner -input tests/passthrough.qml`) — 10 из 10 прошли примерно
  за секунду; с `test_09` про правую кнопку (ниже) — 11 из 11, а с частичной маской
  решения 11 (`test_10`–`test_17`) тестов 17 — 19 из 19 вместе с init и cleanup,
  23.09.2026. Он воспроизводит прежнее
  поведение (левая проглочена, правая проходит), показывает, что `Locked` и `Manual` глотают по-прежнему,
  что `enabled = false` у контейнера отдаёт обе кнопки столу и апплету снизу, что
  включение обратно возвращает перехват и что при отключённом контейнере долгое нажатие
  режим правки не включает.
- **Настоящий стол** (Plasma 6.7.5, Qt 6.11.2): одноразовый считающий апплет, два
  экземпляра рядом, обычный и с привязкой, — родитель печатался как
  `BasicAppletContainer_QMLTYPE_85_QML_105`. Настоящей мышью: обычный насчитал 30
  нажатий, сквозной — 0, и клики попадали на стол. Переключение `editMode` у
  `org.kde.PlasmaShell` по DBus включало обёртку обратно; выход из режима правки —
  отключал снова.

### Правой кнопке нужно ещё одно: стол ищет апплет геометрически

С одной только выключенной обёрткой правый клик по виджету всё ещё открывал меню
**самого виджета**. Стол не доставляет это нажатие апплету — он апплет ищет:
`ContainmentItem::mousePressEvent` (libplasma,
`src/plasmaquick/plasmoid/containmentitem.cpp`, под комментарием «FIXME: very inefficient
appletAt() implementation») перебирает все `PlasmoidItem` и берёт первый, у которого

```cpp
ai->isVisible() && ai->contains(ai->mapFromItem(this, event->position()))
```

— на `enabled` он не смотрит вовсе, так что выключенный апплет для контекстного меню
по-прежнему «на месте». Зато `QQuickItem::contains()` смотрит на `containmentMask`
элемента (qtdeclarative, `qquickitem.cpp`: если маской стоит `QQuickItem`,
`return quickMask->contains(point - quickMask->position())`). Пустой `Item` 0×0 в роли
маски заставляет `contains()` ответить «нет», и стол показывает своё меню, как будто
виджета нет. В `main.qml` монитора и погоды:

```qml
Binding {
    target: root
    property: "containmentMask"
    value: (root.cfg.clickThrough && !root.shellEditMode) ? noHitMask : null
}
Item { id: noHitMask; width: 0; height: 0; visible: false }
```

В режиме правки маска снимается вместе с возвращением обёртки, так что штатные ручки и
меню оболочки работают как обычно. Плеер и визуализатор ставят туда не пустой элемент, а
прямоугольник строки кнопок, так что их собственное меню открывается только над кнопками —
частичная маска, ниже. ⚠️ Почему `Binding`, а не `containmentMask: …` — следующие грабли.
Проверено: `test_09` стенда ставит маску по имени у `ItemContainer`, и
`contains(Qt.point(50, 50))` переключается true → false → true (11 из 11 проходят); на
настоящем столе оба виджета пропускают и правую кнопку, и левую, под играющую музыку, а
визуализатор загрузился без предупреждений QML.

## «PlasmoidItem.containmentMask» is not available in org.kde.plasma.plasmoid 255.255

Записанная декларативно маска на корне апплета — `containmentMask: noHitMask` внутри
`PlasmoidItem { … }` — не загружается, и оба апплета показали это на столе. В журнале
(сокращённо):

```
error when loading applet "org.s1dd1.plaintop" … main.qml:78:5:
"PlasmoidItem.containmentMask" is not available in org.kde.plasma.plasmoid 255.255
```

Свойство существует — это `QQuickItem::containmentMask`, — но несёт ревизию QtQuick 2.11,
а модуль `org.kde.plasma.plasmoid` эту ревизию для своих типов не подключает, поэтому у
`PlasmoidItem` компилятор QML его отвергает.

Работает присваивание по имени:

```qml
Binding { target: root; property: "containmentMask"; value: … }
```

`Binding` по имени идёт через `QQmlProperty`, который ищет свойство во время выполнения и
ревизий не проверяет. Все четыре `main.qml` делают именно так, а `test_09` стенда — то же
самое с `ItemContainer`. ⚠️ Отказывает именно `PlasmoidItem`, а не свойство: у
`ItemContainer` — обёртки — декларативная `containmentMask: …` загружается и работает
(`test_17`, 23.09.2026). Обёртка доступна виджету только как `root.parent`, так что там
это `Binding` по имени в любом случае.

## `/usr/bin/qmltestrunner` — от Qt 5

На этой системе (на базе Arch) `/usr/bin/qmltestrunner` принадлежит `qt5-declarative` и
на файл для Qt 6 отвечает «Library import requires a version» — `qmldir` от Qt 6 он
прочесть не может. Раннер Qt 6 — `/usr/lib/qt6/bin/qmltestrunner` (`qt6-declarative`).

## `left` и `right` у любого `Item` — FINAL

Это линии привязки (anchors). Счётчик `property int left` в `MouseArea` не
компилируется: «Cannot override FINAL property». Счётчики — `nLeft` / `nRight`.

## Обычное окно умеет: `Qt.WindowTransparentForInput` работает под KWin Wayland

Проверено счётчиком на экране: окно с
`flags: Qt.FramelessWindowHint | Qt.WindowTransparentForInput` поймало **ноль** нажатий,
пока по нему щёлкали. Wayland отдаёт ему пустую область ввода — нативный аналог того
трюка с X Shape, который понадобился conky.

⚠️ Цена — размещение: под Wayland окно не может задать себе место. `x` и `y`
игнорируются, KWin ставит окно как считает нужным, поэтому окну-виджету нужно правило
KWin, которое принудительно задаёт место, размер, «держать снизу» и «не показывать в
панели задач».

Оконные хосты, построенные на этом факте, погашены (решение 9) — плазмоид пропускает обе
кнопки сам; сам факт остаётся в силе.

## `SensorDataModel` молча выбрасывает идентификаторы, которых не понял

Просишь 165 датчиков — получаешь 162 столбца: о неразрешённых идентификаторах он не
сообщает, их просто нет, и **все последующие столбцы сдвигаются**. Код, читающий столбец
*n*, получает значение соседа — на s1dPC «температура NVMe» читала вентилятор. Повторная
подписка не помогает, и предела количеству нет (200 идентификаторов ядер разрешаются
нормально).

Что работает: обращаться к столбцам по роли `SensorId`, а не по месту, а всё, что не
однородный массив, брать отдельными объектами `Sensors.Sensor`. Они те же самые
идентификаторы разрешают надёжно и показывают `status` — 2 значит «готов», так что
отсутствующее показание отличимо от нулевого.

## `cpu/all/coreCount` — это не `cpu/all/cpuCount`

`cpuCount` — число физических процессоров, на этой машине 2. `coreCount` — 72. Защёлкнув
длину массивов по ядрам из `cpuCount`, виджет читал две температуры из 72, и выглядело это
ровно как «температура ядер пропала».

## Имена чипов гниют точно так же, как индексы hwmon

В проекте уже запрещено брать датчики по индексу `hwmon`. Имя чипа не надёжнее: после
перезагрузки `lmsensors/nvme-pci-0500/temp1` стал `nvme-pci-0600`, а сетевой интерфейс из
`enp4s0` — `enp5s0`. Виджет, который несёт такой идентификатор в конфиге, замолкает без
ошибки на той самой машине, для которой писался, — про другую и говорить нечего.

Поэтому идентификаторы находятся сами: `SensorTreeModel` перечисляется один раз (здесь 675
записей), сохранённый идентификатор остаётся лишь **предпочтением**, а когда машина его
больше не отдаёт, замену находит шаблон — `^lmsensors/nvme-[^/]+/temp\d+$` находит диск
при любой перенумерации шины.

## В дереве датчиков лежат ещё и шаблоны-регулярки

Среди записей есть `cpu/cpu\d+/temperature`, `gpu/gpu\d+/usage` и
`network/(?!all).*/download` — 11 из 675 на s1dPC. Это шаблоны целых групп, а не датчики,
и подписка на такой не даёт ничего. Отсеивать по метасимволам регулярных выражений
(`( * \ ? [ ] | +`): в настоящем идентификаторе их не бывает.

## Сетевые интерфейсы лежат в дереве в порядке хэша

«Первый интерфейс из дерева» — не выбор, а жребий. ksystemstats хранит устройства в
`QHash` (`SensorContainer` в libksysguard), и при двух подключённых устройствах — Wi‑Fi и
док-станция, два порта — порядок меняется от одного старта демона к другому. Зато мусора в
дереве нет: бэкенд NetworkManager публикует только Ethernet, Wi‑Fi, Bluetooth, модем и
ADSL с активным подключением, бэкенд rtnetlink — только связи `ARPHRD_ETHER` без типа в
состоянии UP. `docker0`, tun (sing-box, WireGuard), veth и `lo` не попадают ни в один: на
s1dPC `nmcli` видит четыре подключённых устройства, а в дереве одно. Прочитано в исходниках
ksystemstats 6.7.5.

Поэтому кандидаты сортируются и ранжируются: сначала шлюз (непустой `ipv4gateway` или
`ipv6gateway` — их заполняет только бэкенд NetworkManager, у rtnetlink они пусты всегда),
потом пройденный трафик (`totalDownload`), потом имя. Ранжируются один раз на набор
интерфейсов, чтобы выбор не прыгал; пробы отписываются сразу после выбора, а при одном
интерфейсе не заводятся вовсе.

## Внутри `Sensors.Sensor` голое `name` — свойство самого датчика

У `Sensor` есть свои `name`, `shortName`, `value`, `unit`, `status` и `enabled`, и
неквалифицированное имя в привязке внутри него ищется сначала там. В делегате со свойством
`name` строка `sensorId: "network/" + name + "/download"` дала `network//download` —
отображаемое имя датчика, пустое до прихода метаданных, — и датчик так и остался в
состоянии Loading; `probe.name` дал `network/enp5s0/download`. Проверено на s1dPC
2026-09-22. Ссылаться на делегат через его `id`.

## `FormLayout` из Kirigami ругается, когда `Repeater` пересобирает детей

`TypeError: Cannot read property 'isSection' of null`, `Cannot read property 'Accessible'
of null`, `Unable to assign [undefined] to int` — по три строки на каждую пересборку,
всякий раз, когда меняется модель `Repeater` внутри `FormLayout`. Воспроизведено файлом на
25 строк, где нет ничего, кроме `FormLayout`, `Repeater` и одной подмены модели: это
собственный шум Kirigami, а не ошибка делегата. Полезно знать до того, как потратишь час
в своём коде, как случилось здесь.

## Список приходит в делегат `Repeater` вариантным списком, а не JS-массивом

`modelData.value` со списком строк: `Array.isArray()` возвращает **false**. Проверка вида
`Array.isArray(v) ? v : []` рисует пустой список, хотя в конфиге две записи, и ничто не
предупреждает — обе ветки допустимы. Копировать по `length`, и тогда один и тот же код
работает и с JS-массивом, и с вариантным списком.

## При загрузке реле может стартовать раньше PipeWire — и одна плохая строка его убивала

Юнит упорядочен после `pipewire.service`, и всё равно при загрузке cava не нашла поток,
вышла и напоследок написала в stdout управляющую последовательность заголовка терминала
(`\x1b]0;cava…`). Реле отдало эту строку в `int()`, поток чтения умер с `ValueError`, а
реле продолжило отвечать по HTTP без cava и без перезапусков — `/state` показывал
`frames: 0, restarts: 0` до следующей перезагрузки. Кольцо выглядело просто молчащим.

Теперь строка, которая не кадр, пропускается, любая ошибка внутри цикла кончается
перезапуском, а не мёртвым потоком, а пока cava не может даже стартовать, перезапуски
отступают до 10 с. Юнит ещё и ждёт `wireplumber` и `pipewire-pulse` — это сужает гонку,
но закрывает её только повтор. Воспроизведено поддельной `cava`, которая печатает ту же
последовательность и выходит: три перезапуска через 2, 4 и 8 с, ни одного traceback.

## PID-файл ничего не знает про автозапуск

Оконные хосты записывали свой pid при запуске из `setup.py`, а запись автозапуска зовёт
`qml6` напрямую и ничего не пишет. После перезагрузки файл устарел: `--status` говорил
«не запущено» про живое окно, а перезапуск старое не трогал и ставил на стол вторую копию.
Теперь окна ищутся в таблице процессов — точный исполняемый файл (`comm` равен `qml6`) и
точный путь к `window.qml` среди аргументов, — и заодно это далеко от `pkill -f`.

## Переприсваивание `var`-карты из многих обработчиков пересобирает всё, что её читает

Каждый из ~25 отдельных объектов `Sensors.Sensor` публиковал значение, копируя карту и
присваивая копию. Карту читает каждая строка монитора, и каждая строка пересобиралась по
разу на каждый датчик в секунду — окно стоило 18 % ядра за текст, который меняется раз в
секунду. Правка карты на месте и пересборка по одному общему тику дали 9 % (4,6 % — сбор,
остальное — отрисовка). То же правило для реестра датчиков: его опрос раз в 10 с теперь
присваивает список, только если тот действительно изменился, а не пересоздаёт все объекты
датчиков каждый раз.

## `Repeater` с JS-массивом в модели пересоздаёт все делегаты при каждой смене массива

Монитор собирает строки новым массивом на каждом тике, а `Repeater` брал этот массив
моделью — и каждый тик уничтожал все 41 строку и строил их заново, вместе с раскладкой
`Text`. Посчитано счётчиком в `Component.onCompleted`: ~57 делегатов в секунду при
интервале 700 мс. Если отдать `Repeater` число (`lines.length`), а делегату читать
`lines[index]`, элементы остаются, а `Text` с неизменившейся строкой ничего не делает.
Окно — с 8,0 % ядра до 4,5 %, картинка на снимках та же.

## Процессорное время дочерних процессов не входит в собственное время родителя

`utime + stime` окна монитора не включали всё, что запускали его источники `executable`, —
после завершения оно уходит в `cutime + cstime`. Скрипт служб стоил 615 мс процессора за
прогон, раз в 15 с: 4,3 % ядра круглосуточно, измерено за 15 часов, и ни в одной прежней
цифре этого не было. Один `pacman -Qu` — 362 мс; теперь он запускается, только когда
меняется база pacman. Мерить вместе с дочерними, иначе вызов команды прячется на виду.

## `ProcessDataModel` читает весь /proc раз в 2 с, что бы ни было задано

Период зашит в libksysguard (2000 мс) и не следует интервалу виджета. `enabled` запускает
и останавливает этот таймер; включение не читает сразу, первое чтение — через 2 с.
Включать на одно чтение за период работает: загрузка CPU считается по настоящему
прошедшему времени — процесс, крутящий одно ядро, показывал 99–100 % и при 2 с, и при
одном чтении раз в 10 с. Цена при ~900 процессах: 3,2 % ядра при 2 с, 1,3 % при 10 с.

## cava считает и в тишине, если не задан `sleep_timer`

Тишина — это нулевые отсчёты, а cava продолжает считать БПФ и выдавать кадры: 3,9 % ядра.
`sleep_timer=N` останавливает её после N секунд тишины, и дальше она смотрит на вход раз в
секунду — 0,35 %. В реле стоял комментарий, что cava засыпает, но саму настройку ей не
передавали, и она не засыпала. Цена — пробуждение: первый кадр приходит через 0,04–1 с
после возвращения звука, измерено подачей в cava FIFO.

## Проверка, сравнивающая с копией времён установки, проходит после любой правки

Общие QML копируются в пакет плазмоида при установке, и `--status` сравнивал установленный
пакет с этой копией — после правки в `shared/` обе были старыми, и проверка говорила
«совпадает». Оконные хосты проверялись только на наличие: окно монитора сутки работало
с `SensorRegistry.qml`, отстававшим от репозитория на одну правку. Теперь `--status`
сравнивает с исходниками, включая реле, и говорит, если окно запущено раньше, чем
разложены его файлы (`ctime` файлов — `copy2` переносит `mtime` исходника; старт процесса
через `/proc/uptime` — `btime` целая секунда и помечал окно, запущенное через 0,05 с после
раскладки).

## xgettext помечает подстановки ki18n как формат JavaScript

Прогнанный по QML с `-L JavaScript`, xgettext помечает строку вида `"%1d"` как
`javascript-format`. Формат не тот: у ki18n подстановки `%1`…`%99`, и русское `"%1д"` после
`msgmerge` выходит «неточным» — во время работы такой перевод не используется.
`po/extract.py` снимает флаг JavaScript и помечает каждую строку с `%1`… как `kde-format`,
который `msgfmt --check` действительно проверяет: перевод, потерявший `%2`, валит сборку.
Проверено на s1dPC 2026-09-22.

## «Форматы» KDE сильнее `LANG` и `LC_ALL`

Чтобы увидеть виджет глазами англоязычного пользователя, под Plasma мало
`LANG=en_US.UTF-8 LC_ALL=en_US.UTF-8 LANGUAGE=en`: слова переключаются, а дата остаётся
«Вторник, сентября 22» и десятичный разделитель — запятой. Интеграция KDE, которую
подгружает Kirigami, накладывает `~/.config/plasma-localerc` («Параметры системы →
Форматы») поверх окружения. С пустым `XDG_CONFIG_HOME` тот же запуск даёт «Tuesday,
September 22» и «9.2 GiB». Для пользователей это правильно — «Форматы» они выбирают
отдельно от языка, — а важно только для проверок.

## Несгенерированная локаль молча выключает все переводы

`locale -a` на s1dPC показывает только C, en_US и ru_RU. Запустите виджет с
`LC_ALL=de_DE.UTF-8 LANGUAGE=de` — glibc не найдёт локаль и откатится на C, а в локали C
gettext игнорирует `LANGUAGE`. Все строки остаются английскими, а дата при этом немецкая:
названия дней и месяцев Qt берёт из собственных данных. На это независимо наткнулись все
четыре прогона переводчиков. Без root локаль собирается во временный каталог, и glibc
направляется туда: `localedef -i de_DE -f UTF-8 $DIR/de_DE.UTF-8`, затем `LOCPATH=$DIR`.
Можно и не трогать `LC_ALL` — под любой сгенерированной локалью `LANGUAGE` соблюдается, —
но тогда дата останется в вашей.

## `/usr/bin/qmllint` — тоже от Qt 5, как `qml` и `qmltestrunner`

Та же ловушка, что с раннером выше, только инструмент другой: `/usr/bin/qmllint` — из
`qt5-declarative`. На файле для Qt 6 он не печатает ничего и выходит с кодом 255 — ни
«неизвестный импорт», ни номера строки, — так что проверка, которая читает вывод, а не код
возврата, проходит как «замечаний нет». Линтер Qt 6 — `/usr/lib/qt6/bin/qmllint`
(`qt6-declarative`), с `-I /usr/lib/qt6/qml` ради импортов Plasma; в `CONTRIBUTING.ru.md`
он записан полностью. Правило для этой системы: инструмент Qt 6 искать сначала в
`/usr/lib/qt6/bin/`.

## `plasmawindowed` — один экземпляр: второй запуск выходит с 0 и молчит

Пока один `plasmawindowed` открыт, `plasmawindowed org.s1dd1.plainweather` тут же
вернулся с кодом 0, ничего не напечатал, а лог, куда его направили, остался пустым — ни
окна, ни ошибки. Выглядело так, будто апплет не загрузился без следа. Дело в уже
запущенном экземпляре: завершить его (или проверить `pgrep -x plasmawindowed`) до запуска
следующего апплета — по одному за раз.

## Плагин power в ksystemstats регистрирует каждую `Solid::Battery` — вместе с мышами и гарнитурами

На настольной машине без батареи в дереве датчиков всё равно появляются записи под
`power/`, стоит подключить беспроводную мышь, клавиатуру или гарнитуру: плагин
регистрирует каждую найденную `Solid::Battery` — под серийным номером устройства, а не
именем, — и у каждой настоящий `chargePercentage`. Батарею от периферии отличает
`capacity` в Вт·ч: у периферии 0. Поэтому блок батареи подписывается на все записи —
ёмкость читается только по подписке — и показывает те, у которых `capacity` > 0; на этом
столе таких нет, и блок прячется. ⚠️ Настоящей батареи под ним ещё не было: проверены
путь скрытия и заглушка с выдуманными значениями.

## В дереве датчиков есть пустая группа `power`, а группы `pressure` нет

`registry.has("power")` на s1dPC даёт true — группа в дереве есть, под ней ничего, — а
`registry.has("pressure")` даёт false, хотя `pressure/cpu/some10Sec` на месте и отвечает.
Появится ли узел группы, решает плагин, так что группа ничего не доказывает ни в ту, ни в
другую сторону. Проверять шаблон листа: `^pressure/cpu/some10Sec$` для блока PSI,
`^power/[^/]+/chargePercentage$` для батарей.

## У `font` в QML нет `families` в Qt 6.11

Список запасных — сначала настроенное семейство, потом `monospace` — у QML-шного `font`
не записать: у типа-значения в Qt 6.11 нет свойства `families`, присваивание не проходит.
С одним `font.family` не установленное семейство уходит в подстановку fontconfig, а та не
обязана выбрать моноширинное — и колонки разваливаются. Плеер спрашивает у
`Qt.fontFamilies()`, есть ли настроенное семейство, и берёт `"monospace"`, когда его нет.

## У `XMLHttpRequest` в Qt нет таймаута

`req.timeout` игнорируется, `ontimeout` не приходит никогда: запрос к хосту, который не
отвечает, висит открытым. Виджет погоды держит рядом с запросом `Timer` на 10 с и зовёт из
него `abort()`; прерванный запрос приходит в `readyState` DONE со `status` 0, как любой
неудавшийся, так что один обработчик обслуживает оба случая. ⚠️ Чтение `status` до DONE
бросает «Invalid state» — сначала проверить `readyState`, потом смотреть статус. Поиск на
странице «Место» делает то же.

## `new Date("YYYY-MM-DD")` — это полночь по UTC

Дата ISO без времени разбирается как UTC: `new Date("2026-09-24")` — это
2026-09-24T00:00Z. Западнее Гринвича этот момент по местному времени ещё 23-е, и день
недели из него — вчерашний: строки прогноза уехали бы на день для половины мира. Собирать
дату из частей, `new Date(y, m - 1, d)`: это местная полночь, и день недели верен везде.

## `msginit` для zh_CN оставляет `Plural-Forms: nplurals=INTEGER`

`msginit -l zh_CN` пишет в заголовок заглушку `Plural-Forms: nplurals=INTEGER;
plural=EXPRESSION;` вместо правила, и `msgfmt --check` — ворота установки — отвергает
каталог, пока заголовок не поправить руками: `Plural-Forms: nplurals=1; plural=0;` для
китайского и японского. Это важно теперь, когда `po/extract.py` сам заводит недостающий
каталог через msginit: заголовок свежего каталога смотреть до первой установки.

## Источник `services` работает, показан блок или нет, — новые источники отключаются с блоком

`services.sh` запускается раз в 15 с с тех пор, как блок написан, включён тот или нет: у
его `DataSource` постоянный `connectedSources`. Источник `health` завязан на блок: без
включённого блока `health` его `connectedSources` пуст, а число строк ошибок — аргумент
скрипта, так что он не читает больше, чем показано. ⚠️ Одно свойство, а не два: когда
«включён» и «строки» читались отдельными свойствами, команда пересобиралась дважды на
каждую смену `blocks`, и первый скрипт убивался на бегу — воспроизведено в отдельном
стенде. Каждый новый источник завязывать так же; старый остаётся как есть, пока его
кто-нибудь не тронет.

## `FontMetrics.height` — не высота строки `NativeRendering`

При 10 pt JetBrains Mono `FontMetrics.height` говорит 17,14 px, а `Text` с
`renderType: Text.NativeRendering` выходит высотой 18 px — хинтинг округляет строку до
целых пикселей. Апплет, рассчитанный на пять строк по метрике, на четыре пикселя короче,
и последняя строка обрезана. Мерить скрытый `Text` тем же шрифтом и брать его
`implicitHeight`; оба новых виджета считают размер доски так. Измерено в оффскрин-хосте
23.09.2026.

## Частичная `containmentMask` на обёртке: кнопки берут мышь, остальное пропускает

Решение 8 выключает обёртку, а с ней и каждую `MouseArea` внутри — у сквозного плеера не
было кнопок (решение 11). Обход — в собственном поиске целей Qt:
`QQuickDeliveryAgentPrivate::eventTargets` пропускает элемент, чей `contains()` говорит
«нет», но всё равно заходит в его детей. Поэтому обёртка остаётся включённой и получает
`containmentMask` — один прямоугольник строки кнопок, в координатах обёртки: внутри него
обёртка — цель, как у любого апплета, — клик доходит до `MouseArea` под знаком, долгое
нажатие включает режим правки, — а вне его обёртка пропускается, нажатие попадает на стол
или на апплет под ним, и наведение тоже. Тот же прямоугольник ставится `PlasmoidItem`
ради правой кнопки (геометрический поиск стола, выше), оба — через `Binding` по имени,
оба — `null` в режиме правки. Пока строка скрыта — нет плеера на шине или кнопки
выключены, — прямоугольник 0×0, и проходит всё. Так делают
`player/package/contents/ui/main.qml` и `spectrum/package/contents/ui/main.qml`;
прямоугольник берётся из `PlayerView.controlsRect` и переводится через `mapToItem()`.

Проверено на стенде, `tests/passthrough.qml`, тесты 11–15: контейнер с маской, текстом и
строкой кнопок 120×24 поверх другого апплета — внутри прямоугольника клик считают кнопки,
вне его — стол или апплет под ним; правая кнопка доходит до стола с обеих сторон;
наведение идёт по той же границе (`test_13`: доставка наведения заходит в каждого видимого
потомка, что бы ни говорил родитель, так что область с `hoverEnabled` на весь апплет
забрала бы наведение везде — область кнопок берёт его только над собой); долгое нажатие
внутри включает режим правки, снаружи — нет; маска, снятая в `null`, возвращает полный
перехват. Второй, одноразовый стенд положил настоящий `PlayerView.qml` внутрь
скомпилированного `ItemContainer`: 11 из 11. ⚠️ Стенд без экрана; настоящие клики на живом
столе — по-прежнему проверка пользователя. Проверено 23.09.2026, plasma-workspace 6.7.5,
Qt 6.11.2.

## `Text` с `textFormat` по умолчанию принимает левую кнопку

Под частичной маской это и есть ловушка. `Text`, созданный с `textFormat` по умолчанию
(`AutoText`), сохраняет из конструктора `acceptedMouseButtons = LeftButton`
(`qquicktext.cpp`: `init()`; только `setTextFormat()` опускает его до `NoButton`), то есть
он — цель указателя, и для него срабатывает `childMouseEventFilter` обёртки, не спрашивая
`contains()`: запускается таймер долгого нажатия. Само нажатие уходит дальше на стол, и
отпускание тоже — тому, кто держит захват на столе, мимо фильтра, — так что таймер никто
не останавливает, и обычный клик по тексту через 800 мс переводит обёртку в режим правки.
Без маски обёртка сама цель: берёт захват и гасит таймер в своём `mouseReleaseEvent`; вне
маски — нет. `test_10` показывает обе половины: режим правки через 1,2 с с текстом по
умолчанию и никакого — с `Text.PlainText`.

Поэтому под частичной маской мышь не должен принимать никто, кроме кнопок: `textFormat:
Text.PlainText` у каждого `Text` (компонент `Line` в `PlayerView.qml`, уведомление о реле
у визуализатора) либо `enabled: false` у поддерева, в котором нечего нажимать. Штрихи
кольца — `Rectangle`, ввод не принимают.

## Координаты `containmentMask`: считаются только x/y самой маски

`QQuickItem::contains()` делает `quickMask->contains(point - quickMask->position())`:
точка — в координатах маскируемого элемента, вычитаются только `x`/`y` маски, а её
родитель — как и видимость — не спрашивается вовсе (`qquickitem.cpp`, Qt 6.11.2). Значит,
`Item` маски может лежать где угодно в дереве, невидимый, лишь бы его `x`/`y`/размер были
прямоугольником в координатах обёртки; и маска ограничивает только обёртку, а не её
поддерево — `MouseArea` попадает под клик по собственной геометрии. `test_16` показывает
обе вещи с отступом 20 у контейнера: содержимое и кнопки съезжают в 60..180, обе маски
остаются на 40..160, клик по 50 берёт обёртка, по 170 — кнопки. Отсюда `maskRect()` в
обоих хостах: прямоугольник строки переводится в `root.parent` для обёртки и в `root` для
`PlasmoidItem`, а позиции по цепочке читаются заранее, чтобы привязка следовала за
перемещением. Декларативная `containmentMask: …` у `ItemContainer` загружается
(`test_17`) — отказывает именно `PlasmoidItem`, грабли выше.

## На стенде режим правки переставляет контейнеры

Отпускание в режиме правки меняет порядок наложения: `ItemContainer::mouseReleaseEvent`
зовёт `AppletsLayout::positionItem`, а менеджер сетки затем ставит контейнер перед
соседом справа или снизу (`GridLayoutManager::assignSpaceImpl`, «Reorder items tab
order») — на стенде «row» с маской оказывался под апплетом «beneath», чья `MouseArea`
дальше забирала всё, и следующие клики уходили туда по причине, никак не связанной с
маской. `resetRow()` переприсваивает контейнеру родителя (`parent = null`, потом снова
раскладка) — это ставит его последним, снова сверху, — и восстанавливает геометрию.
Стоит знать любому тесту, который пускает `ItemContainer` в режим правки.

## Голый `i18n()` в общем файле идёт по домену хоста

`player/shared/PlayerView.qml` копируется в два пакета, а его строки идут через голый
`i18n()`. Вызов разрешается через домен перевода того плазмоида, который загрузил копию:
один и тот же файл внутри plainplayer показывает каталог плеера, внутри plainspectrum —
каталог визуализатора. Проверено 23.09.2026. Поэтому `po/extract.py` перечисляет
`player/shared` под обоими доменами, и строка, добавленная туда, попадает в два каталога —
забудешь один, и визуализатор покажет английский там, где плеер переведён. Это
противоположность `monitor/shared/`, чей `KI18nContext` несёт зашитый домен: для файла с
двумя хостами образец — голый вызов.

## Метки `barRow` — три знака

`barRow(label, value)` дополняет и режет метку до трёх знаков, чтобы колонка процентов не
ездила, — блок дисков попросил `root` и получил `roo`. Теперь строка принимает
необязательную ширину метки: диски передают четыре, а полоска отдаёт один знак
(`bar(value, width)`), чтобы колонка не сдвинулась. В четыре влезают `root`, `home`,
`data`, `boot`; более длинный последний элемент пути режется. Корневая точка — `root`, а
не `/`, намеренно: полоска рядом тоже из косых, и `/   //` читалось как одно целое.

## В JavaScript QML нет часовых поясов: `toLocaleString` игнорирует `timeZone`

У движка JS в Qt нет `Intl` — `typeof Intl` даёт `undefined`, — а параметр `timeZone`
молча отбрасывается: `d.toLocaleString("en-US", { timeZone: "Asia/Tokyo" })` печатает
машинные 17:00 для момента, который в Токио — 21:00, без ошибки. Проверено 23.09.2026 на
`/usr/lib/qt6/bin/qml`, Qt 6.11. Ряд MET Norway идёт в UTC, и чтобы нарезать его на дни
места, нужно смещение места — машина может стоять в другом поясе. Смещение есть у движка
`time` в Plasma (`org.kde.plasma.plasma5support`): любое имя IANA там — источник, а его
`Offset` — текущее смещение этого пояса от UTC в секундах, с летним временем; незнакомое
имя получает смещение машины (проверено в тот же день). Виджет погоды подключает второй
`DataSource` к `timezone`, который сохранил геокодер, и сдвигает моменты UTC на это
смещение прежде, чем брать дату (`localDate` в `Sources.js`). У введённого или угаданного
места пояса нет — берётся машинный.

## MET Norway отвечает 403 на `User-Agent` по умолчанию

`XMLHttpRequest` в Qt шлёт `Mozilla/5.0`, если не сказано иное, и `api.met.no` отвечает на
это 403: их условия требуют User-Agent, называющий приложение. Qt даёт поставить его через
`setRequestHeader("User-Agent", …)`, так что источник шлёт
`plainweather/0.1 github.com/highscrren-dotcom/plaintop` и получает 200 — проверено
23.09.2026 в виджете для Берлина и Екатеринбурга и ещё раз через `curl -A`: 403 с
`Mozilla/5.0`, 200 со строкой виджета. Условия ещё и ограничивают координаты четырьмя
знаками после запятой; `build()` округляет.

## У 304 нет тела — никогда не `JSON.parse` его

С `If-Modified-Since`, равным последнему `Last-Modified`, `api.met.no` отвечает 304, если
ничего не изменилось: `status` 304, `responseText` пустой (`body=0` у curl).
`JSON.parse("")` бросает исключение, так что обработчик, который сначала разбирает, а потом
смотрит на статус, считает «ничего нового» сбоем и начинает отступать. Виджет разбирает
только 200; на 304 оставляет показанное, берёт новый `Expires` и считает ответ свежим.
`Expires` читается относительно заголовка `Date` самого сервера, а не часов машины, и
следующий запрос ждёт его — плюс 5 с и не дольше часа, что бы ни стояло в заголовке.
Проверено 23.09.2026: второй запрос того же места получил 304, а `Expires` сервера стоял
примерно через 30 минут.

## Visual Crossing отдаёт пятнадцать дней, если даты не названы, — и считает их

Timeline API без диапазона дат в пути возвращает пятнадцать дней прогноза, а бесплатный
тариф считает каждый день ответа записью — из тысячи в сутки: показаны три строки,
засчитаны пятнадцать, за каждый запрос. Поэтому `build()` называет даты — от сегодня до
сегодня плюс `days − 1`, по местной дате места, — а источник обновляется раз в 30 минут
вместо 15. ⚠️ Это из документации Visual Crossing, а не из запуска: настоящего ключа не
было, проверены поддельный ключ (401 → `· неверный ключ`) и парсер на образце ответа.
Записано, потому что меняет форму запроса.

## «офлайн» в заголовке погоды может быть сетью, а не виджетом — а источник это настройка

На машине автора заголовок какое-то время показывал `· офлайн`, хотя поиск на странице
«Место» работал: выход туннеля был в России, и оттуда TCP до `api.open-meteo.com` не
устанавливался вовсе, а `geocoding-api.open-meteo.com` — другой хост, у другого хостера —
и `api.met.no` отвечали (измерено 23.09.2026 и ещё раз при написании этих строк: таймаут
соединения у одного, 200 у остальных). Виджет держал кэшированный прогноз и продолжал
повторять запрос по своему отступу, как и велит решение 10. Факт про сеть, а не про
виджет; записан, чтобы следующее «погода сломалась» начиналось с сети, — и это причина,
по которой у виджета четыре источника (решение 13): когда используемый отрезан,
«Источник» на странице «Место» переключается на другой, MET Norway без ключа.

## Обработчик изменения видит производные привязки до их пересчёта

`onDaysChanged` сравнивал производное `dayCount` (привязка от `days`) с числом строк — и
всегда видел старое значение: обработчик, подключённый раньше привязки, срабатывает до её
пересчёта. Увеличение числа дней не вызывало запрос. Сравнивать нужно исходное значение,
о котором обработчик, либо откладывать через `Qt.callLater`.

## 304 — не «ничего не изменилось» для прогноза, обрезанного по часу запроса

met.no отвечает 304 на `If-Modified-Since`, пока не пересчиталась модель (от 35 минут до
полутора часов), но каждое тело 200 начинается с часа запроса. Сохранение прежнего разбора
при 304 замораживало «сейчас» и строки дней на часе последнего 200, а обновление возраста
это прятало. Виджет держит сырое тело последнего 200, при 304 разбирает его заново с записи,
покрывающей текущий час, и шлёт `If-Modified-Since`, только пока это тело в памяти.
